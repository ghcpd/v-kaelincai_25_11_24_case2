Description This experiment evaluates AI models’ ability to implement and optimize a ride-detail API that must expose fare breakdown data without regressing legacy clients. Current pain points: • GET /rides/{rideId} returns only total fare; clients issue extra GET /rides/{rideId}/fare-items calls. • Driver and rider apps perform 2–3 serialized requests, leading to 6–8 second load times in poor networks. • Legacy clients cannot be updated quickly, so the existing response schema must remain valid when the new parameter is absent. • Weak-network scenarios exacerbate latency and failure risk due to multiple round trips. • Lack of unified response makes caching and metric tracking harder. The improved version (Project B) must deliver: • Extended GET /rides/{rideId} supporting includeFareBreakdown=true to return a full fare breakdown in one call. • Default includeFareBreakdown=false path that preserves legacy payload (no fareBreakdown field). • Efficient data-access layer minimizing additional queries when the breakdown is requested. • Configurable caching or memoization to prevent redundant downstream fetches. • Strict validation and sanitation of fare items (type, label, amount) to avoid hidden vulnerabilities. • Robust handling of malformed ride IDs, non-string fields, nested breakdown structures, and unexpected fare item types. • Quantitative reporting on latency reduction, request-count savings, and coverage of edge cases. Key evaluation criteria: • Correctness of the enhanced API implementation and backward compatibility. • Performance improvement (reduced round trips, latency, resource usage). • Handling of malformed inputs, hidden vulnerabilities, and non-standard data types. • Accuracy of fare breakdown composition and total-fare reconciliation. • Automated test coverage for normal, edge, and invalid flows. • Reproducible environment with single-command execution. • Quantitative metrics: average latency delta, additional-query reduction, edge-case success rate.
